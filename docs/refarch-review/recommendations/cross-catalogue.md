## 2. Deviations read together

Forty deviation entries across the thirteen files. Four findings:

**2.1 — "The sandbox is not drawn as a frame" appears three times, and its stated reason has been formally repudiated. Defect.** `endpoint-coding-agent-first-party.yaml`, `endpoint-coding-agent-third-party.yaml` and `endpoint-personal-agent.yaml` all carry a deviation whose reason is "a frame inside a band reads as a second boundary of the same kind." ONTOLOGY §4a quotes that exact claim and says: *"That was wrong, and it cost the catalogue its most important control recommendation."* Worse, the personal agent's copy is now factually false about its own file — that drawing **does** draw `Sandbox` as a `kind: boundary` block with `harness`, `memory` and `toolPlane` as children. This is a rule-level fix, not three exceptions: delete the personal agent's deviation, and either draw the sandbox frame on both coding agents (containment is real there — `sandboxedTools` says "when isolation is on") or rewrite their deviations with a reason the ontology has not disowned.

**2.2 — Stale deviations in `endpoint-coding-agent-third-party.yaml`. Defect.** Three of its five entries have decayed: (a) "The vendor's cloud sits in the external band" — it does not; `vendorService` is in `zoneVendor`, a band this deviation predates. (b) "The vendor session crosses the egress control…" references the `Egress control` component the denylist removed, and duplicates the adjacent "The vendor's own path is admitted, not inspected" entry — which itself now restates ONTOLOGY §4a's sanctioned-vendor table rather than deviating from anything. (c) The two-model-paths deviation ends "…lose the relay that flow F1 is about" — this file has no flows, and the flows mechanism was deleted catalogue-wide (§4b). One decision (vendor path admitted, not inspected) is stated twice; two references point at things that no longer exist.

**2.3 — Three files still carry the deleted `flows:` mechanism. Defect.** `endpoint-personal-agent.yaml` (F1–F8), `saas-enterprise-ai-chat.yaml` (F1–F4) and `saas-low-code-agent-builder.yaml` (F1–F6) retain full `flows:` sections with ids, `threats:` and `controls:` lists. The build ignores the key (no parser in `scripts/build-data.ts`), so this is ~250 lines of dead data that contradicts ONTOLOGY §4b ("Everything else was deleted") and will silently rot — the personal agent's F8 note already carries walkthrough-grade content (the heartbeat's read-only action class) that exists nowhere in the live walks. Migrate what is load-bearing into step/pin notes; delete the rest.

**2.4 — Unrecorded absorption in `cloud-training-pipeline.yaml`. Judgement.** `capabilityDataSanitization` is inline (embodied by `Curation & filtering`, per `vocabulary.yaml`), is pinned on `dataOrigins->corpus` with no such block drawn, and the file's only recorded deviation covers the *other* absorbed scan (artifact scanning at the training job). The pin note argues the absorption well — it belongs in `deviations:`, where the mechanism says it goes.

## 3. Name reuse

**3.1 — The `aiGatewayTraffic` pack asserts a "Model proxy" on three gateways that broker no inference. Defect.** The low-code builder established the precedent: a gateway that carries no model traffic drops the pack, lists its real items, and records a deviation — and `patternModelPath` gained `requiresItem: Model proxy` to make that honest. Three other drawings did not follow: `cloud-remote-mcp-server.yaml` (the file itself says "There is no model anywhere in this service"), `saas-enterprise-ai-chat.yaml` (no Model provider block exists on the drawing; the vendor calls its own model), and `saas-managed-agent-runtime.yaml` (same). All three gateways display a Model proxy item that is false, and a "Skills broker" that is doubtful on at least the MCP publisher's inbound edge. Byte-identical is the pack's promise; here the identical bytes are the lie.

**3.2 — The cloud-band "Tool services" block diverges between families where the pack should hold. Judgement.** The three cloud agents draw it as `pack: toolServicesRemote` (MCP servers, APIs & connectors, A2A peer agents — the pack's own note says A2A belongs in our cloud band "including one we host ourselves"). The three endpoint agent drawings and the personal agent hand-list the same block with two items and no A2A (`hostedTools` in both coding agents; `internalTools` in the personal agent). Either an endpoint-reachable cloud tool surface genuinely offers no A2A peers — in which case say so once — or this is exactly the "similar in four, subtly different in the fifth" drift the pack exists to prevent. Rule 9 says pick one.

**3.3 — `vocabulary.yaml` carries ten live registrations no active drawing uses, and one is a duplicate concept. Defect (vocabulary hygiene).** `Chat surface & uploads`, `Curation & filtering`, `Evaluation & red teaming`, `Model registry`, `Serving & consumers`, `Managed memory`, `Managed sandbox`, `Managed tool gateway`, `Connected systems`, `User-connected systems` — zero uses each. Two consequences: (a) `Chat surface & uploads` duplicates `Browser`, whose own `when` says "Do not dress it up as a 'chat surface'" — one of the two must be marked `deprecated:`, or the next author picks by coin-flip; (b) `Evaluation & red teaming` and `Model registry` are orphaned because the drawings dropped content the vocabulary (and the training pipeline's own *title*, "Fine-tuning and model **registry** pipeline") still promises — see finding 1 on `riskEvaluationBenchmarkManipulation`. The rest should be deprecated with pointers, per rule 5 of §4c. Related: the `capabilityEnforcement` inline map names embodying components that exist nowhere in any registry or drawing — `Artifact scanning`, `Identity provider`, `Agent identities` — so those inline requirements can only ever be satisfied by absorption, which makes the map's promise empty for them.

**3.4 — `Inference runtime` carries two different CoSAI anchors. Defect (minor).** Vocabulary registers it with `componentModelServing`; `endpoint-local-inference.yaml` overrides to `componentTheModel` while `cloud-self-hosted-inference.yaml` keeps `componentModelServing`. Same title, two crosswalks — a reader relating the two drawings through the risk map lands on different components. Pick one (ModelServing is right; the loaded model is an item).

## 4. Pin distribution smells

**4.1 — The first-party coding agent's pins were copy-pasted from the third-party file, vendor and all. Defect.** In `endpoint-coding-agent-first-party.yaml` — the drawing whose entire thesis is *"there is no vendor"* and whose first deviation says the missing column "has no counterpart here" — the `capabilityAuditLogging` pin at `aiGateway` reads "Our own session record, **fused with the vendor's export**", the `govObservability` block note repeats it, and the `capabilitySecretsManagement` note says "**the vendor's cloud** never holds a standing org credential." Three notes describing a component the drawing exists to lack. The family rule says the two files differ only in the vendor column; these are the leftovers of enforcing that mechanically.

**4.2 — Duplicate pins at one locus in `cloud-agent-workflow.yaml`. Defect (minor).** `riskSensitiveDataDisclosure` is pinned twice at `state`, and `capabilityAiDlp` twice at `state` — the second of each existing only to say "the specialists journal too", which the subagents-as-one-block deviation already establishes. Two identical tags on one block is the over-pinning §6.3 warns about; fold each pair into one note.

**4.3 — Enterprise AI chat pins no prompt-injection risk while citing two prompt-injection incidents as sources. Defect.** `saas-enterprise-ai-chat.yaml` sources EchoLeak and ShadowLeak — both zero-click prompt-injection exfiltrations through exactly this archetype's connector path — and pins `capabilityPromptInjectionDefense` at `vendor->extTools`, yet `riskPromptInjection` appears nowhere on the drawing (the only active architecture with an agentic loop that lacks it). A control pinned with no risk it answers, on the drawing whose incident record is the strongest in the catalogue for that risk. Pin it at `vendor->extTools`.

**4.4 — Architectures light relative to their prose. Judgement.** The training pipeline (6 risks) states a memorisation-disclosure story in its description that has no pin (see `capabilityPetTooling`, §1). The managed runtime describes cross-user memory scope as "the component most likely to be switched on without a decision" and pins the control (`capabilityMemoryProtection`) but no risk for it. The pattern in both: the description knows things the pin layer never absorbed.

**4.5 — Not a smell: the govObservability audit+kill pair on every drawing.** This looks like copy-paste but is the sanctioned standard pin pattern (ONTOLOGY §7 checklist item 3). The one divergence — the personal agent citing `capabilityKillSwitch` from the *Identity services* call-out and pinning it at the gateway — is argued in its notes (revocation-as-stop) and I read it as deliberate. Judgement: fine, but a one-line deviation would spare the next reviewer this paragraph.

## 5. Catalogue shape

**5.1 — `distinguishedBy` written against drawings that no longer exist. Judgement.** The field is defined as the argument against a *neighbour*, but five architectures argue partly or wholly against retired entries: the chat agent against "the embedded retrieval assistant" and "the realtime voice agent"; the MCP server against "a third-party MCP server you consume" and "an AI-augmented API backend"; the training pipeline against "the batch pipeline"; the low-code builder against "an internal AI platform you operate". Worst case is `saas-enterprise-ai-chat.yaml`, whose two contrasts ("the tenant-wide assistant", "shadow AI") are **both** parked — it never distinguishes itself from its two live SaaS siblings, so a reader comparing the three active SaaS pages gets no help from the field that exists for that purpose. No active *pair* is actually confusable after reading both files — the drawings themselves separate cleanly — but the fields should argue against the live catalogue, with retired contrasts moved to notes.

**5.2 — One boundary genuinely blurring: the chat agent contains the single agent. Judgement, no change demanded.** `cloud-chat-agent.yaml` draws `Triggers & schedules` with an edge whose note concedes a scheduled run "makes it the single-agent workflow wearing a chat interface." Its `distinguishedBy` ("remove the human from the turns and you are in that architecture") survives because the note names the hand-off honestly — but this is the pair to watch: one more unattended feature drawn on the chat agent and the two pages describe one system.

**5.3 — Missing archetype: the agentic browser, retired for a reason that has aged. Judgement.** The recorded reason (`archAgenticBrowser`: "An agent with a browser tool set — a tool-calling use case, not a distinct architecture") was fair when the browser was a tool an agent drives. In the current product class the browser *is* the harness: the ingress is every webpage rendered (an unbounded author set, like the personal agent's senders), the actuation surface is every session the user is signed into, and no drawing in the catalogue carries that combination — the coding agents' "Computer use" item is the nearest and its notes never state the always-authenticated-web story. The retirement reason addressed the tool-set framing, not the admission-model framing; by the ontology's own standard (the first/third-party split was justified by "graph-level differences" in custody and admission), this one now has them. Propose reactivation from `disabled/endpoint-agentic-browser.yaml` be considered — explicitly as a revisit of the recorded reason, not a re-proposal in ignorance of it.

**5.4 — Internal shape defect worth listing here: the managed runtime's description contradicts its own drawing. Defect.** `saas-managed-agent-runtime.yaml`'s description says "The provider **blocks** on this diagram are drawn because they are documented, separately addressable products" — the diagram draws exactly one provider block (`Managed runtime`), with memory and sandbox folded in as items, and the vocabulary's `Managed memory` / `Managed sandbox` / `Managed tool gateway` registrations orphaned (§3.3). Either the folding is right (likely, per the three-zone rule) and the description plus vocabulary should say so, or the decomposition the description promises should be drawn. As it stands, prose and graph disagree about the file's central representational choice — and it is the only architecture besides the action agent with an empty `deviations:` ledger, which for this file is not plausible.
