# G7 — Cross-drawing pin consistency audit (17 architectures)

Scope: `_cross.md` plus all 17 `arch*.md` packets. I checked them against three things:
(a) the formal MITRE/D3FEND definitions and the `cap-*` implementation text in `data/overlay/specializations.yaml`;
(b) the repo's own placement rules: `data/ONTOLOGY.md` §2 and §3, and the `mitigationEnforcement` classification in `data/reference/vocabulary.yaml` (inline means it pins on the embodying component, embedded means it pins where it is enforced, management means a governance call-out plus a chip on that call-out; zone-1 vendor internals are never pinned);
(c) the recorded `deviations:` in `data/reference/architectures/*.yaml`. Where a finding is a recorded deviation, I say so.

I made no edits to the repo. The scan script is at `scratchpad/g7/scan.cjs`; it compares every pin with the enforcement classification.

Drawing abbreviations follow the packets: Single agent, Multi-agent, Chat agent, A2A federation, Remote MCP server, Self-hosted inference, Training pipeline, Browser AI, First-party agents, Third-party agents, Personal agent, Local runtime, Enterprise chat, UI/low-code runtime, API/SDK runtime, Coding & desktop runtime, Persistent agents.

---

## A. Classification vs practice (catalogue-level drift that produces the per-drawing inconsistencies)

### A1. cap-agent-kill-switch is classified two ways, and the drawings split to match (HIGH)
- `vocabulary.yaml` lists `cap-agent-kill-switch` under **embedded**. `ONTOLOGY.md` §2 lists "kill switch" as a **management** example.
- 12 drawings pin it on the Observability & response governance block (management practice). Those are Single agent, A2A federation, Multi-agent, Chat agent, Browser AI, First-party agents, Third-party agents, Enterprise chat, Coding & desktop runtime, UI/low-code runtime, API/SDK runtime and Persistent agents.
- Personal agent pins it on the **AI gateway** and calls it out under **Identity services**. This is a recorded deviation.
- The Personal pin's note covers only "revoking the agent's identity cuts off every model and tool call". The cap's own composite rule says "a pin that does only one of them claims only that one", so this pin is revocation, which is D3-CR.
- Standard: reclassify the cap as management. Pin it on Observability & response, with the call-out in the same group. On Personal agent, replace the gateway chip with **D3-CR on the AI gateway** (D3-CR's inline embodiment list includes AI gateway), and keep a kill-switch chip on Observability & response.

### A2. cap-data-access-governance is classified inline@AI gateway, but none of its 6 pins are on a gateway (HIGH)
- Single agent, Multi-agent and Chat agent pin it on the Tool services→Enterprise data edge. Remote MCP server pins it on the MCP service→Enterprise data edge. UI/low-code runtime pins it on the **Enterprise data block**. Enterprise chat pins it on the Vendor chat service (a zone-2 block).
- None of these absorptions are recorded.
- The cap's own implementation text places it "between the orchestrator and the data sources … applied at the data source", which is embedded.
- Standard: reclassify as embedded. The standard location is the **Tool services→Enterprise data** edge. Move the UI/low-code runtime pin from the block onto that edge, which exists on that drawing. The Enterprise chat zone-2 pin stays.
- Remote MCP server's use ("per-tenant scoping enforced in our own code", over writes as well as reads) is general access mediation more than retrieval governance. It is acceptable, but a candidate for the parent **D3-AMED**.

### A3. cap-mcp-tool-integrity is classified management, but all 8 drawings pin it on the data path, and only one records it (MED-HIGH)
- Pins: Single agent, Multi-agent and Chat agent on Agent harness→AI gateway; A2A federation on the AI gateway block; First-party and Third-party agents on Native tools→AI gateway; Personal agent on **Native tools→Private pkg registry**; Remote MCP server on Tool definitions→MCP service (this one is recorded).
- The cap's own text ("sits at the point where the harness or runtime loads a tool definition") supports pinning on the data path, so the classification is what's wrong.
- Placement also differs inside the endpoint family. Personal agent uses the mirror edge, while First-party and Third-party use the gateway edge.
- The First-party note ("harness, extension and skill versions pinned against the mirror") describes the mirror edge but is pinned on the gateway edge. Harness version pinning is also not MCP tool integrity: it falls under AML.M0014/D3-FA.
- Standard: reclassify as embedded. Pin on the edge where tool definitions reach the MCP client, which is **Agent harness→AI gateway** (or Native tools→AI gateway for local servers). Move the supply-path pinning wording to D3-FA/AML.M0014 on the registry edge.

### A4. cap-retrieval-grounding-checks is classified inline@AI gateway, but all 3 pins are on the Memory & state block (MED)
- Single agent, Multi-agent and Chat agent pin it on Memory & state, with no recorded deviation.
- The cap text ("in the retrieval corpus and embedding store") supports the block.
- Standard: reclassify as embedded on **Memory & state**.

### A5. D3-APA is classified inline@{Authorization server, Identity provider, Identity binding}, but 10 of its 14 pins are elsewhere (MED)
- Pins elsewhere: the trigger edges on Single agent and Multi-agent; Channel bridges on Personal agent; Tool services[vendor] on Enterprise chat; Vendor service on Coding & desktop runtime and Persistent agents; the Source control block on Coding & desktop, API/SDK and Persistent; the consumer→platform edge on UI/low-code runtime.
- Only Coding & desktop runtime records an absorption.
- The meaning also drifts. On Single agent, Multi-agent and Chat agent it means *runtime grant binding at ingress* ("whose authority a run carries", "a delegated grant scoped to the session"). Elsewhere it means *administered policy* (admin consent, trigger policy, pairing policy, who may create agents).
- Standard: treat D3-APA as administered policy, which is zone-2 configuration plus an Identity services call-out. Express the per-request delegation on ingress edges with D3-CTS or D3-AMED.

### A6. cap-sensitive-data-redaction and cap-output-encoding have embodiment lists that are too narrow for the cap text (LOW-MED)
- `cap-sensitive-data-redaction` is inline@AI gateway only, but 6 of its 7 pins are elsewhere, and the cap text itself names "the endpoint agent or browser" as the locus for user input.
- `cap-output-encoding` is inline@AI gateway, but the only pin (Chat agent) is on the Application front end, which is what the cap text describes.
- Standard: widen the embodiment lists to include Browser, Native tools/Sandbox, Application front end and Messaging relay.

## B. Semantic drift / parent–specialisation misuse

### B1. cap-staged-rollout-gate on Local runtime is evaluation-only, sits in the wrong group, and is placed differently from Self-hosted inference (HIGH)
- The note says only "evaluate what the weights actually do before promoting". There is no canary and no rollback.
- The cap text says "only the evaluation gate is model validation (its AML.M0008 parent)". Training pipeline correctly uses **AML.M0008** for the same gate.
- It is called out under Observability & response. Every other use is under Supply-chain assurance.
- Self-hosted inference pins the same concept on Storage→Inference runtime "load".
- Standard: change it to **AML.M0008**, pin it on the **Storage→Inference runtime "load"** edge (the same absorption Self-hosted inference records), and call it out under Supply-chain assurance.

### B2. cap-agent-egress-control on the Remote MCP Authorization server is misused (HIGH)
- The pin is SSRF blocking of client-metadata discovery fetches by an OAuth server. That component is not an agent and is not an agent execution location.
- The Authorization server is outside the cap's embodiment list (AI gateway, Native tools, Sandbox, Browser). The absorption is recorded, but the ID is still wrong.
- Standard: use the parent **D3-OTF** on the Authorization server.

### B3. AML.M0004 on the A2A partner edge points the wrong way (MED-HIGH)
- The A2A federation pin sits on AI gateway→Peer agent (partner), which is outbound with the reply returning: "only our side opens it". On that edge we are the caller.
- AML.M0004 limits callers of *our* AI service. Limiting our own fan-out to a peer is **AML.M0036** ("limit … parallel tasks, delegation depth, downstream spending").
- Standard: use AML.M0036 on the partner edge. If inbound peer rate limiting is meant, put AML.M0004 on the two-way **AI gateway↔Peer agent (vendor)** edge, where peers invoke our skills.

### B4. AML.M0029 and cap-agent-action-policy-enforcement name the same mechanism (MED)
- Chat agent uses cap-agent-action-policy-enforcement@AI gateway for "mutating actions are refused unless the call carries an approval bound to this action".
- Enterprise chat and API/SDK runtime pin **AML.M0029** on AI gateway→Tool services for the identical mechanism ("our gateway refusing the write without it"). Neither of those drawings pins the action-policy cap.
- Standard: pin AML.M0029 at the approval surface (the approver or user edge, or Source control). Pin the gateway refusal as cap-agent-action-policy-enforcement@**AI gateway**.

### B5. AML.M0028 notes drift away from tool-permission configuration (MED)
- On Multi-agent, AML.M0028 on AI gateway→Tool services reads "each delegation hop carries a narrower grant than its parent". That is delegation narrowing, and it duplicates D3-CTS on Supervisor→Subagents on the same drawing.
- On Single agent, AML.M0028 reads "named, parameter-validated actions with declared blast radius and a compensating transaction". That is catalogue design and parameter validation (cap-agent-tool-registry, or AML.M0033).
- Standard: limit AML.M0028 notes to least-privilege, per-tool grants on the tool surface, as Chat agent and the SaaS drawings word it.

### B6. cap-agent-tool-registry is used for an allowlist and for discovery, not as the registry (MED-HIGH)
- On First-party and Third-party agents the gateway pin means "a managed allowlist of connectors and tool servers, enforced from our gateway". Enterprise chat and the SaaS drawings pin that same idea as **AML.M0028** on AI gateway→Tool services.
- On Personal agent the gateway pin means "every daemon that reaches the crossing is inventoried there", which is discovery (cap-shadow-ai-discovery).
- The cap is management. Seven drawings pin it on the Supply-chain assurance block. Six place it elsewhere: the AI gateway on First-party, Third-party and Personal; the Browser block on Browser AI; the vendor platform on UI/low-code runtime; the deploy edge on API/SDK runtime (recorded).
- Standard: pin cap-agent-tool-registry on **Supply-chain assurance**. Re-ID the gateway allowlists as AML.M0028 on AI gateway→Tool services. Re-ID Personal agent's pin as cap-shadow-ai-discovery.

### B7. D3-NI on the Training job is really an egress allowlist (LOW-MED)
- The note reads "deny-by-default egress from the job: the mirror, the corpus store and the artifact store are the whole allowlist". That is outbound filtering. The same control is D3-OTF or cap-agent-egress-control on every other drawing.
- Self-hosted inference uses D3-NI correctly, for isolating the serving plane.
- Standard: use **D3-OTF** on the Training job.

### B8. D3-CTS on the Browser AI profile is a stretch (LOW-MED)
- The pin means "a dedicated profile with few signed-in origins and no saved passwords". That is credential minimisation and isolation, not transmission scoping.
- Everywhere else D3-CTS means token exchange, audience binding or vault substitution.
- Standard: use **D3-CH** on the Browser profile for "no saved passwords and few origins". Reserve D3-CTS for exchange or audience binding.

### B9. D3-AA is pinned on the agent being authenticated, not on the component that verifies it (MED-HIGH)
- Single agent and Chat agent pin it on the Agent harness block; Multi-agent pins it on Subagents. Their notes describe identity *issuance* ("a distinct workload identity per agent").
- A2A federation and Remote MCP server pin it on the Authorization server. Self-hosted inference pins it on the AI gateway. Those are the verifiers, and they match the inline list (Authorization server, Identity provider, AI gateway, Agent identities).
- Standard: pin D3-AA on the **AI gateway** in the agent drawings, which is where the per-agent workload credential is presented, and leave identity issuance to the Identity services call-out.

## C. Wrong component type

### C1. D3-EI on the Coding & desktop runtime vendor Native tools contradicts its own note (MED-HIGH)
- The note says it is "a provider guarantee we verify by assessment, not a setting we toggle". That is zone 1, which `ONTOLOGY.md` §3 says is never pinned.
- Standard: remove the pin and cover it through cap-ai-vendor-assessment on Managed runtime[vendor].
- API/SDK runtime's D3-EI is acceptable only because of the "worker we run" variant. Its note should say the pin is zone-2/self-hosted only.

### C2. cap-agent-action-policy-enforcement is pinned on the vendor config plane, not where the decision happens (MED)
- On Third-party agents and Browser AI it sits on the Vendor service block. Both notes say "the per-action decision is enforced inside the harness / agent".
- The cap is inline@AI gateway, and these pins are not recorded.
- Browser AI pins AML.M0028 at the enforcement point (Native tools), "set in the vendor console". So one drawing uses two conventions.
- Standard: pin on the endpoint **Agent harness** or Native tools, with a recorded absorption. Keep the vendor console as the config surface named in the note.

### C3. D3-MFA is enforced at our IdP but pinned on vendor objects, in two different ways (MED)
- Browser AI and Third-party agents pin it on the Vendor service block. Persistent agents pins it on the Remote device[user]→Vendor service edge.
- All three notes say "MFA enforced at our IdP". The inline list is Authorization server, Identity provider and Identity binding. None of these placements is recorded.
- Standard: pin D3-MFA in one consistent place, the **user→Vendor service sign-in edge** with a recorded absorption (or the Identity provider block where one is drawn). Call it out under Identity services.

### C4. cap-input-guardrails on the SaaS Managed runtime→Source control edge has no customer-owned enforcer (MED)
- Coding & desktop runtime, API/SDK runtime and Persistent agents pin "hidden-character and HTML-comment filtering … before the session reads them" on this edge.
- The edge carries git through a GitHub App directly. No customer inline component is on it, and the filtering runs inside the vendor's session.
- Standard: make it a zone-2 pin on Managed runtime[vendor] where the product exposes it, and otherwise cover it through cap-ai-vendor-assessment. Record the absorption either way.

### C5. D3-CR (Remote MCP server) is pinned on Observability & response although it is enforced at the Authorization server (MED-HIGH)
- D3-CR is inline@Authorization server, Identity provider, AI gateway or Agent identities. The note says revocation is enforced by "introspection, short lifetimes and refresh tokens revoked".
- Standard: pin on the **Authorization server[cloud]** and call it out under Identity services.

## D. Placement inconsistency within families

### D1. D3-EI is missing on Single agent and Chat agent (MED-HIGH)
- Single agent, Multi-agent and Chat agent draw identical Native tools blocks, each with a "Sandboxed tools" item and the same "network policy … not just the sandbox" egress note.
- Only Multi-agent pins D3-EI. All three pin riskInsecureIntegratedComponent on that block.
- Standard: add D3-EI on the **Native tools (Sandboxed tools)** block on Single agent and Chat agent.

### D2. Controls on the agent-to-gateway crossing switch between edge and block across families (MED)
- **D3-CH** sits on the Agent harness→AI gateway edge on Single agent, Multi-agent and Chat agent, but on the **AI gateway block** on First-party, Third-party and Personal agents. The concept is the same: brokered credentials, no standing key.
- **AML.M0036** sits on the **AI gateway block** on Single agent, Multi-agent and Chat agent, but on the harness→AI gateway edge on First-party and Personal agents. The notes on both say "ceilings on the crossing".
- Both caps are inline@AI gateway.
- Standard: pin both on the **AI gateway block**.

### D3. AML.M0031 and persistence redaction are pinned on the block on some drawings and the edge on others (MED)
- AML.M0031 sits on the Memory & state block on Single agent, Multi-agent and Chat agent. A2A federation (same family) and Browser AI, First-party, Third-party and Personal agents pin it on Native tools→Memory & state.
- cap-sensitive-data-redaction for "what may be persisted" sits on the Memory & state block on Multi-agent but on Native tools→Memory on Chat agent. Single agent has no such pin.
- Standard: pin AML.M0031 on the **Memory & state block**, which is where the scoping is enforced. Pin persistence redaction on the **Native tools→Memory & state** edge, which is the write path.

### D4. Management caps sit on the AI gateway in the endpoint family and on governance blocks elsewhere (MED)
- cap-agent-tracing is on the AI gateway on Browser AI, First-party, Third-party and Personal agents. The other 9 drawings put it on Observability & response.
- cap-shadow-ai-discovery is on the Agent harness, Browser or Inference runtime blocks on 5 endpoint drawings, but on Observability & response on Enterprise chat.
- Both caps are management, and none of these placements is recorded.
- Standard: pin both on **Observability & response**. The gateway tap and the endpoint sensor go in the note.

### D5. D3-FA is pinned at ingest in four different ways (LOW-MED)
- The agent drawings and Local runtime pin it on the external→store/mirror ingest edge.
- Self-hosted inference pins it on the Storage block, although its Model sources→Storage "weights in" edge is the analogue of Local runtime's hub→Storage edge (recorded).
- Training pipeline pins it on the Private pkg registry block, although its Base model & deps→registry edge exists.
- Standard: pin on the **external→mirror/store ingest edge** everywhere.

### D6. Endpoint coding agents have no gate pins on Source control (MED)
- On First-party and Third-party agents, riskRogueActions on Native tools→Source control says "branch protection and review at the host are what stop it landing", but no control is pinned there.
- The SaaS siblings pin AML.M0029 (draft PR and review) and AML.M0028 (scoped token) on the Source control block.
- Standard: add AML.M0029 on **Source control[cloud]** on First-party and Third-party agents, plus AML.M0028 where a scoped credential is used.

### D7. cap-output-guardrails coverage is uneven (LOW-MED)
- Personal agent pins it on AI gateway→Model provider because "no hosted product applied it". First-party agents is in the same raw-provider-API position and has no such pin.
- Single agent, Multi-agent and Chat agent pin riskInsecureModelOutput on gateway→provider with no output check.
- Standard: pin cap-output-guardrails on the **AI gateway** wherever a raw provider API is brokered.

## E. Call-out group fit

### E1. AML.M0005 is cited under different groups (MED-HIGH)
- Self-hosted inference cites it under Secrets & key management; Training pipeline under Policy & authorization. Local runtime pins it but cites it nowhere.
- Standard: **Policy & authorization**. The control is access control on model and data stores.

### E2. D3-CTS is cited under different groups (MED)
- 8 drawings cite it under Secrets & key management. Remote MCP server cites it under Identity services, and A2A federation cites it under both.
- Standard: one group. I recommend **Secrets & key management**, since that is the majority and it sits beside D3-CH. Remove the duplicate on A2A federation.

### E3. Misfits in Observability & response (MED)
- **cap-model-documentation** (Training pipeline) is a registry and lineage record. It belongs under Supply-chain assurance, next to AML.M0023, and the drawing has a Model registry block on the release path.
- **D3-AVE** (Remote MCP server, Self-hosted inference) is vulnerability enumeration. Its sibling D3-SYSVA is cited under Supply-chain assurance on the same Remote MCP drawing.
- **D3-CR** (see C5) belongs under Identity services.
- **cap-ai-threat-modeling** (Local runtime) is a risk assessment, better placed under Supply-chain assurance next to vendor assessment.

### E4. AML.M0013 and D3-APA are each cited in two groups on one drawing (LOW-MED)
- AML.M0013 is in both Supply-chain assurance and Secrets & key management on Training pipeline. Standard: Supply-chain assurance only, with signing keys mentioned in the note.
- D3-APA is in both Identity services and Policy & authorization on Enterprise chat. Standard: Identity services only.

### E5. Call-out completeness varies by drawing for the same capability (MED)
- cap-agent-action-policy-enforcement is cited on 6 drawings but not on Single agent, Multi-agent or Chat agent, where it is pinned.
- cap-input-guardrails is pinned on 13 drawings and cited on none.
- AML.M0031 is pinned on 13 drawings and cited once (Persistent agents).
- cap-agent-egress-control is not cited on Coding & desktop runtime or API/SDK runtime, but is cited on Persistent agents.
- cap-agent-kill-switch is not cited on Third-party agents.
- AML.M0028 and AML.M0029 are not cited on the endpoint drawings, Enterprise chat (AML.M0029) or Enterprise chat/Personal (AML.M0028).
- D3-FA is cited on the inference drawings but not on the five agent drawings.
- Standard: a fixed capability→group map, applied wherever the implementing service is in the governance band:
  - **Identity services**: D3-AA, D3-APA, D3-MFA, D3-CR.
  - **Secrets & key management**: D3-CH, D3-CTS, AML.M0012.
  - **Policy & authorization**: AML.M0004, AML.M0005, AML.M0028, AML.M0029, AML.M0031, AML.M0036, cap-agent-action-policy-enforcement, cap-agent-egress-control, D3-OTF, cap-data-access-governance, cap-input-guardrails, cap-output-guardrails, cap-sensitive-data-redaction.
  - **Supply-chain assurance**: AML.M0008, AML.M0013, AML.M0014, AML.M0023, AML.M0025, D3-FA, D3-SYSVA, D3-AVE, cap-agent-tool-registry, cap-mcp-tool-integrity, cap-staged-rollout-gate, cap-ai-vendor-assessment, cap-model-documentation, cap-ai-threat-modeling.
  - **Observability & response**: AML.M0024, cap-agent-tracing, cap-agent-kill-switch, cap-shadow-ai-discovery, D3-WSAA, D3-PA.

## F. Risks pinned where they cannot materialise

### F1. riskAgenticDelegationConfusedDeputy is on Tunnel connectors that hold no upstream authority (MED-HIGH)
- Enterprise chat, Coding & desktop runtime, API/SDK runtime and Persistent agents pin it on the Tunnel connector. Their own notes say the tunnel is "transport only — it does not authenticate to the upstream" and that "the grant is issued at our gateway". The deputy acts where that grant is exercised.
- The reverse happens on UI/low-code runtime. Its tunnel *does* hold cached connection credentials ("reads with each connection's stored credential whoever is asking"), which is the textbook confused deputy, but there it is pinned as riskSensitiveDataDisclosure.
- Standard: on the four drawings, pin it on **AI gateway→Tool services**. On UI/low-code runtime, re-pin the tunnel as riskAgenticDelegationConfusedDeputy.

### F2. riskShadowAndUnknownAgents is pinned on the governed path or a user edge (MED)
- On API/SDK runtime it sits on the Agent definition & code→Managed runtime "deploy" edge. That is the reviewed path; a shadow agent is by definition one that bypasses it.
- On Coding & desktop runtime it sits on the Remote device[user]→Vendor service edge.
- Persistent agents (Vendor service) and UI/low-code runtime (platform) pin it on the vendor block that hosts the agent population.
- Standard: pin it on the **vendor block hosting the agent population**: Managed runtime[vendor] on API/SDK runtime, Vendor service[vendor] on Coding & desktop runtime.

### F3. Lower-confidence risk placements (LOW-MED)
- **riskSensitiveDataDisclosure on the Training pipeline Evaluation & red teaming block.** Memorised data is disclosed by the served artifact; evaluation is where it is *detected*. Standard: pin it on the Model registry or Storage artifact.
- **riskShadowAndUnknownAgents on the A2A federation AI gateway.** The note describes unreviewed *external* peer cards, which fits riskToolSourceProvenance on gateway→Peer agent better.
- **riskSensitiveDataDisclosure on Native tools→AI gateway (First-party and Third-party agents).** That is the inspected path to our own servers. The exfiltration the note describes is the direct Open web edge, which already carries the risk.
- **riskModelSourceTampering on the Self-hosted inference Model sources[external] block.** Training pipeline and Local runtime pin it on the inbound edge.
